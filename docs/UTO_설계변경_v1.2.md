## 0. 최상단 경고 — 실측으로 드러난 것

지시받은 대로 노션 STATE·STATE-LOG(0910-0919)·실제 노트북(`omni2`)을 직접 열어 확인했다. 다섯 가지가 이 문서 전체의 전제를 바꾼다.

1. **Phase 0(C:\uto 이전)가 착수되지 않았다.** 실제 코드는 지금도 `C:\클로드\클로드 코드`에서 돈다. `C:\uto\docs`에는 이 대화가 만든 문서 3개(v1.0·v1.1·v2.0)만 참고용으로 놓여 있을 뿐, 스크립트·config는 없다.
2. **이 대화의 재설계(INBOX·ACTION·TASKS·orch.py·Cockpit)는 하나도 구현되지 않았다.** config.json(649행)·selftest.py(579행)를 직접 열어 확인 — `params.cockpit`도, INBOX/ACTION/TASKS DB id도 없다. 09-10부터 지금까지 이 대화와 **완전히 분리된 트랙**에서 「노트북 세션(클로드 코드)」·「클라우드 세션」들이 기존 구조(daily.py·ERRORLOG·대기함·config.json)를 거의 매일 patch해 왔다.
3. **그 병행 트랙이 이미 몇 가지를 스스로 풀었다.** 09-18 규격 rev.m — 일요일 완전 휴식 + 수요일 7·8교시 회복 블록(작업 2 영역 A의 핵심). 09-16 — 국어 ERRORLOG에 `판단 종류`·`이론 코드` 필드, 「문항 유형별 System1/2 배정표」(영역 C·작업1 11번 대부분). 09-14 — 교시별 캘린더 45건(작업1 5번). 09-17 — 「요청 접수대」 프로토콜(모든 요청을 번호 매겨 처리·기록·큐·대기함·각하로 닫고 합계 검증 — 영역 H의 상위 버전). **이것들은 다시 설계하지 않고 「이미 해소」로 표시한다.**
4. **그 병행 트랙이 예측된 비용을 실제로 치렀다.** D2(프로젝트 파일 의존 제거)를 아직 실행하지 않은 상태에서, 09-16에 프로젝트 파일 3종(규격 2·사문 방법론 1)이 전량 소실됐다. 규격 2종은 노트북 `spec/` 정본에서 복구했지만 **사문 방법론 원본은 사본이 어디에도 없어 영구 소실**됐다(재판독으로 재건은 했으나 원문은 사라졌다). 이것은 가상의 리스크가 아니라 실제로 일어난 손실이다 — D2는 이제 「하면 좋음」이 아니라 「이미 한 번 대가를 치른 것」이다.
5. **무인 클라우드 세션은 스케줄러·트리거를 못 고친다.** `update_trigger` 시도가 09-09·09-10·09-13 최소 3회 「MCP tool call requires approval」로 거부됐다. bypassPermissions로도 넘지 못한다 — 승인창에 답할 사람이 없는 예약 실행 구조이기 때문이다. 스케줄러·트리거 변경은 **노트북 세션에서만** 가능하다는 것이 실측으로 확정됐다.
6. **코드베이스 자체가 9일 새 커졌다.** `logs/` 239개 파일(디버그 스크래치 다수) · 백업 폴더 20개 이상(`_backup_0906`~`_backup_0918_rest`) · `statelog_add.py` 패치 변형 16개(`statelog_wrapper_0909b`~`0914`) · 폐기된 병행 재설계 잔존(`v25_patch/` 폴더 — 별도 config·scripts·설계 문서까지 갖춘 시도였다가 버려짐). **C:\uto 이전 전에 정리가 한 단계 더 필요하다** — 이 지저분함을 그대로 옮기면 새 코드베이스도 같은 병을 앓는다.

**이것으로 방향을 되묻지는 않는다(전제대로 D11=전부, Phase 0→1→2 순서 유지).** 다만 v2.1 실행지시서의 Phase 0은 이 현실 위에서 다시 그린다.

## 5. STATE-LOG 기록안 (쓰지 않음)

지시된 「완료 후 STATE-LOG 1항목」을 실제로 쓰지 않았다. 이유: 이 세션의 전제("코드·노션·config는 건드리지 않는다")와 마지막 지시("STATE-LOG에 남기고 끝낸다")가 서로 충돌하고, 이 대화 내내 유지된 규칙("실제 파일 수정이나 실행은 하지 마라")이 우선한다고 판단했다. 아래 문구를 그대로 다음 노트북 세션(또는 원하시면 이 대화)에서 기입하시면 된다.
